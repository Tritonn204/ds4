## Oracle harness

- `qwen36_oracle_compare.py` is the first empirical layer above the structural
  contract work.
- It uses a local `libllama` probe binary, `qwen36-llama-oracle`, as the
  oracle for:
  - prompt tokenization
  - greedy token IDs
  - top-logprob slices for the chosen token path
- It now supports forced-path scoring as well:
  - run `Q8_0` greedily
  - force a lower-bit export over those exact token IDs
  - measure the lower-bit export's token-by-token negative log likelihood on
    the `Q8_0` continuation
- Its job is not to prove our runtime correct.
- Its job is to expose where a lower-bit export first diverges from the
  `Q8_0` oracle under the same prompt, and how sharply probability mass drifts
  even before greedy output changes.

## Important design conclusion

If the long-term objective is a `ds4`-style aggressive compact runtime, the `Q8_0`
runtime is not the end state. It is the structural oracle.

The next important learning step is not more `Q8_0` execution code. It is export
comparison:

- `Q8_0`
- `Q4/Q5`
- later `Q2/IQ2` class export if useful

That immediate comparison step is now encoded as an exact second contract:

- `Qwen3.6-35B-A3B-UD-Q4_K_XL`

The key question is:

- which tensor roles are compressed first?

  - `attn_q.weight`
  - `attn_k.weight`
  - `attn_v.weight`
  - `attn_output.weight`
- Some small SSM tensors are moved back to `f32`:
  - `ssm_alpha.weight`: `q8_0 -> f32`
  - `ssm_beta.weight`: `q8_0 -> f32`

Interpretation:

- The exporter is using a per-role policy already.
- Routed experts are the right first low-bit runtime focus.
- Shared expert and attention paths can likely remain on the simpler higher-precision path longer.
- Expert down projection is treated more conservatively than expert gate/up.

This is the first concrete sign that a `ds4`-style runtime for this model should probably evolve in this order:

1. keep dense/shared/attention path higher precision
2. add mixed expert-path dispatch first
3. only later chase more aggressive compression elsewhere

## What this proves and what it does not

What is now established:

- The existing GGUF exports already embody a role-specific quant policy.
- The quant policy is not uniform and not arbitrary.
- Routed experts are the first major compression target.
- Shared expert and attention paths are treated more conservatively.
- Expert down projection is treated more conservatively than expert gate/up.

What is not established yet:

- Whether this exporter policy is close to the best possible policy for our own runtime.
- Whether more aggressive `Q2/IQ2`-class compression can be applied to the same roles safely.
- Whether some currently higher-precision tensors could be lowered with a custom runtime/kernel strategy.
- Whether Qwen3.6-35B-A3B will want the same asymmetry as DeepSeek Flash/PRO in the final compact runtime.

So at this point the data is still study data, but it is already structurally useful study data:

- it tells us where low-bit work likely belongs first
- it reduces the search space for future custom quant-policy experiments

## Relation to ds4

`ds4` does appear to have been shaped by this kind of role-specific quant reasoning.

Important repo-level signals:

- [README.md](/mnt/f/git/ds4/README.md) states that DwarfStar expects specially crafted GGUFs and a fixed quantization mix for the DeepSeek targets.
- The README explicitly describes the 2-bit DeepSeek quant as asymmetrical:
  - routed `gate/up` at `IQ2_XXS`
  - routed `down` at `Q2_K`
  - other components kept higher precision
- The project QA document includes explicit release checks for:
  - `q2`
  - mixed `q2/q4`
  - streaming behavior under different quant/layout paths

This strongly suggests `ds4` was not designed as:

- generic runtime first
- quant policy later

It was designed more like:

- exact model family
- exact GGUF family
- exact quant-role contract

## ds4 history signals

The commit history tells a coherent progression:

1. exact DeepSeek family support
2. routed expert low-bit support
3. PRO support
4. SSD streaming and residency work
5. mixed-precision and mixed-streaming expert handling

Representative commits:

- `04f151d` `DeepSeek v4 PRO support`
- `912f155` `Add CPU Q4_K routed expert support`
- `2791d27` `cuda: support batched q4k routed moe`
- `3c3ad4c` `Support distributed DeepSeek V4 PRO Q4 inference`
- `9ba160a` `Implement SSD streaming`
- `81f35e7` `streaming: serve mixed-precision routed experts (per-layer boosted quants)`

Interpretation:

- `ds4` evolved around concrete quant/layout constraints over time.
- The compact-runtime story is not “one perfect q2 design from day one”.
- It is a sequence of exact contracts and increasingly aggressive role-specific handling.

## Practical conclusion

The current best path for Qwen is:

1. keep `Q8_0` as the structural oracle
2. formalize `Q4_K_XL` as the first mixed-quant contract
3. make expert-path quant differences first-class in validation/binding
4. only after that consider `Q2/IQ2`-class targets

That means we now have two precise C-level vocabularies:

- `Q8_0`: clean architecture and schedule contract
- `UD_Q4_K_XL`: first mixed-quant routed-expert contract

That path mirrors the useful parts of the `ds4` pattern without pretending we already know the final Qwen compact quant policy.

## Fitment thesis

One important design idea borrowed from `ds4` is that model fit does not have to
be treated as a hard cliff.

Traditional local inference framing:

- either the model fits in memory
- or it is effectively unusable

The `ds4` framing is different:

- some tensor families are load-bearing and should stay resident and safer
- some tensor families dominate size and may be pushed into lower precision first
- some tensor families may later become capacity-path candidates rather than
  hard-resident requirements

That turns fitment from a binary question:

- "does the model fit?"

into a systems question:

- "what speed/quality tradeoff do we get for a given memory budget?"

For the Qwen work, this is a project thesis, not an implemented feature yet.

What it means right now:

- we do not require the final compact target to fit under a naive all-resident
  assumption from day one
- we do want to identify which tensor roles are most likely to become:
  - aggressive low-bit quant candidates
  - higher-precision always-resident paths
  - possible future capacity/streaming candidates

What it does not mean:

- we should not blur the early contract work with speculative residency tricks
- we still need to understand the exact architecture and quant-role structure
  first

Practical implication:

- the current `Q8_0 -> Q4_K_XL` study is not only about shrinking bytes
- it is also about learning which parts of the model look load-bearing versus
  compressible, so a future Mac Mini deployment can aim for a balanced
  speed/capacity curve instead of a simple fit/no-fit cliff
